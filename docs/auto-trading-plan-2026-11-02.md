# LTH 자동매매·체결 자동 반영 구현 계획

작성일: 2026-11-02 · 구현 전 요구사항 확인용

최신 정정: 매수 가격 상한은 현재가 **+20%**이며, 이를 초과한 주문을 +20% 선으로 낮춘다.

추가 구현 요청: 상태 탭 네비게이션 바로 아래 토글, 주문 탭의 별도 API 주문·확인 팝업·성공/오류 표시, 주문 최소 1초 간격, 토글과 독립된 수동/API 체결 조회. 구현 결과와 운영 조건은 [사용·운영 안내](meritz-app-operations.md), [검증 기록](meritz-verification-2026-11-02.md)에 정리했다.

**이 문서는 계획이다. 이번 작업에서는 앱 코드·DB·운영 설정을 변경하거나 주문을 전송하지 않는다.**

## 1. 이해한 요청

자동매매를 켠 전략은 미국 정규장 개장 시점에 메리츠 현재가를 조회하고, LTH의 **오늘 주문 가이드**로부터 실제 주문을 만든다. 매수 가격 상한과 보완매수 범위를 적용한 뒤 접수 결과를 기록한다. 다음 날 아침 기존 차트 갱신 작업과 함께 실제 체결을 조회해 LTH에 반영한다.

| 항목 | 반영할 내용 | 구분 |
|---|---|---|
| 자동매매 옵션 | 앱 안에서 ON/OFF | 요청 사항 |
| 실행 시점 | 미국 정규장 개장 시점 | 요청 사항 |
| 주문의 출처 | 기존 오늘 매수·매도 가이드, 주문 유형 유지 | 요청 사항 |
| 매수 가격 조정 | 현재가의 **+20%를 초과하면 +20% 선으로 낮춤** | 사용자 최신 정정으로 확정 |
| 높은 매도 주문 | 현재가보다 **20% 이상 높은 매도는 제외** | 요청 사항 |
| 하락보완매수 | 현재가의 **-10% 이상인 가격까지만** 제출 | 요청 사항 |
| 수량 합산 | 상한 가격으로 내려오는 기본·보완매수 수량을 합산, 중복 주문 제외 | 예시의 취지에 대한 설계안 |
| 아침 처리 | 차트 갱신 + 실제 체결 조회 + 체결 입력 + 전략 상태 갱신 | 요청 사항 |
| 알림 | 매수 주문 접수 완료 / 체결 반영 완료 / 오류·경고 | 요청 사항 |
| 알림 도착 위치 | 앱 내부 기록 + **아이폰 잠금화면 푸시** | 추가 답변으로 확정 |

토글은 **전략별로 두는 안**으로 정리했다. 처음 확인할 종목은 SOXL이며, TQQQ에도 같은 가격 조정 규칙을 적용할지는 구현 전에 확인한다.

## 2. 현재까지 확인한 범위

- 메리츠 토큰 발급과 SOXL·TQQQ 시세 조회는 이 대화에서 실제 호출에 성공했다.
- SOXL 1주·$80 LOC 주문 코드는 미리보기와 모의 응답 테스트를 통과했다. 실제 주문은 전송하지 않았다.
- 실제 주문 접수 → 실제 체결 조회 → LTH 반영의 전체 연결은 아직 검증하지 않았다.
- 현재 앱에는 자동매매 설정·증권사 주문번호 저장·체결 동기화·잠금화면 푸시 기능이 없다.
- 현재 알림은 페이지 안에서 잠깐 표시하는 `Toast`이며, 백그라운드 푸시가 아니다.

## 3. 메리츠 가격 제한 확인과 사용자 실주문 관찰

**SOXL 주문가격이 현재가에서 20% 이상 벗어나면 반드시 거절된다는 정확한 규정은, 이번에 확인한 메리츠 공식 자료에서 찾지 못했다.**

메리츠 Open API 안내에는 상품별 주문 착오 방지 기준과 경고 주문 재확인 절차가 있다고 명시되어 있다. 하지만 확인한 해외 매수 API 명세·공식 오류 안내·미국 시장 안내에는 SOXL 정규장 LOC에 적용되는 일률적인 ±20% 수치, 기준 시세, 매수·매도별 방향이 명시되어 있지 않았다. 따라서 사용자가 MTS에서 겪은 제한이 API에도 동일하게 적용된다고 단정하지 않는다. 다른 증권사의 제한 수치도 메리츠의 근거로 대체하지 않는다.

추가로 사용자가 **현재가 약 $81에서 $105 주문은 정상 접수되고 $110 주문은 거절됐다**고 알려주었다. 기준 가격이 모두 $81이었다고 가정하면 $105는 약 +29.63%, $110은 약 +35.80%다. 이는 30% 부근의 제한 가능성과는 부합하지만, 이 두 관찰만으로 정확히 30%가 경계라고 확정할 수 없다. 실제 주문 시점의 기준 시세·거절 코드·상세 메시지는 별도 확인이 필요하다. 이 관찰은 사용자 제공 정보이며 이번에 직접 재현한 결과가 아니다.

구현에서는 두 가지를 분리한다.

1. **사용자가 정한 LTH 실행 규칙:** 매수 +20% 상한 / 높은 매도 +20% 이상 제외 / 보완매수 -10%까지만. 이는 계획에 확정해 반영한다. 현재가 $81의 매수 상한은 $97.20이다.
2. **메리츠 실제 접수 제한:** 메리츠 공식 답변 또는 기존 거절 응답의 코드·상세 메시지로 추가 확인한다. 제한을 알아내기 위한 실계좌 시험 주문은 이번 계획 작성에서 수행하지 않는다.

특히 **매도 가격이 현재가보다 20% 높으면 제외한다는 것은 사용자 전략의 실행 규칙**이다. 증권사가 그 방향의 매도를 반드시 거절한다는 뜻은 아니다. +20%로 조정하더라도 시세 변화·증권사 기준가·계좌 조건 때문에 접수가 보장되지는 않는다.

공식 근거: [메리츠 API 이용 안내](https://openapi.imeritz.com/intro), [해외 매수 API 명세](https://github.com/meritz-securities/open-api/blob/a93c6409db73ea97ad15f7b7186f36c9f32ecd89/openapi.json), [공식 오류 안내](https://github.com/meritz-securities/open-api/blob/a93c6409db73ea97ad15f7b7186f36c9f32ecd89/docs/errors.md).

## 4. 매일 실행할 시간

기준 시간대는 `America/New_York`, 거래일은 **미국 시장 거래일**이다. 한국시간 23:30을 일 년 내내 고정하지 않는다.

| 구분 | 미국 동부시간 | 한국시간 |
|---|---|---|
| 일반적인 정규장 개장, 표준시 | 09:30 EST | 같은 날 23:30 |
| 일반적인 정규장 개장, 서머타임 | 09:30 EDT | 같은 날 22:30 |
| 일반적인 정규장 마감, 표준시 | 16:00 EST | 다음 날 06:00 |
| 일반적인 정규장 마감, 서머타임 | 16:00 EDT | 다음 날 05:00 |

- 주말·미국 휴장일은 주문하지 않는다. 조기 폐장과 특별 휴장도 시장 일정으로 구분한다.
- 개장 시분에 작업을 시작하고, 개장 후 유효한 현재가를 확인한 직후 주문한다. 개장 전 캐시 가격을 그대로 쓰지 않는다.
- LOC는 **개장 때 접수하고 종가 조건으로 체결되는 주문**이다. 개장에 즉시 매수하는 시장가로 바꾸지 않는다. 기존 가이드의 LIMIT·MOC도 유지한다.
- 앱이 닫혀 있어도 서버에서 실행한다. 브라우저 타이머에 의존하지 않는다.
- 개장 작업이 누락됐다고 장중 임의의 시간에 뒤늦게 실행하지 않는다. 허용 지연 범위 밖이면 해당 거래일을 보류하고 경고한다. 허용 범위는 구현 전 확정한다.

근거: [메리츠 미국 시장·LOC 안내](https://home.imeritz.com/mobile/content/overseas/usa.html), [NYSE 거래시간·휴장·조기 폐장 일정](https://www.nyse.com/markets/hours-calendars).

### 현재 아침 작업과 실행 환경

현재 `vercel.json`에는 `/api/cron/market-candles`가 `10 21 * * 1-5`로 등록되어 있다. UTC 월~금 21:10이므로 한국시간으로 **화~토 오전 06:10**이다. 이 시각을 아침 체결 반영의 기본 시작점으로 재사용하는 안이다. 실제 운영에서 최근 실행됐는지는 이번 작업에서 조회하지 않았다.

개장 작업은 별도로 필요하다. Vercel Cron을 사용한다면 UTC 13:30 / 14:30 후보를 두고 뉴욕 현지시각·거래일·당일 실행 기록으로 실제 한 번만 실행하도록 설계할 수 있다.

다만 Vercel 공식 문서상 Hobby는 시 단위 실행 정밀도여서 개장 시분 요구에 맞지 않는다. 최초 계획 단계에서는 요금제·스케줄·배포를 변경하지 않았다. 이후 구현·배포 승인에 따라 개장과 5분 후 점검은 기존 Supabase Cron으로 등록하고, 아침 작업은 기존 Vercel Cron을 유지했다. 정각의 특정 초까지 보장하는 것으로 표현하지 않는다. 최종 운영 설정은 `meritz-app-operations.md`를 참고한다.

근거: [Vercel Cron 정밀도와 요금제](https://vercel.com/docs/cron-jobs/usage-and-pricing).

## 5. 개장 시 주문 생성 순서

1. 자동매매 ON 여부, 거래일·개장 시각, 전일 체결 반영 완료 여부를 확인한다.
2. 동일 계좌·전략·거래일의 중복 실행을 차단한다. 연결 계좌와 종목, LTH 상태 및 메리츠 주문 가능 금액·보유수량을 대조한다.
3. 기존 계산 엔진으로 오늘 주문 가이드를 만든다. 가격 조정 전에 원본 가이드와 전략 버전을 저장한다.
4. 개장 후 현재가 `P`를 조회하고 조회 결과·수신 시각을 저장한다. 0·누락·조회 오류는 주문 중단과 경고로 처리한다.
5. 매수 상한, 보완매수 하한, 매도 제외 규칙을 적용한다.
6. 같은 방향·주문 유형·실제 가격으로 합쳐진 주문의 수량을 합산하고, 어떤 원본 주문이 포함됐는지 연결한다.
7. 주문 가능 금액과 수량, 매수·매도 주문 간 상충 여부를 확인한다.
8. 각 주문을 한 번씩 제출하고 응답·주문번호·접수 상태를 개별 저장한다.
9. 제출 대상 매수 주문이 모두 정상 접수됐을 때 ‘매수 주문 접수 완료’ 알림을 보낸다. 실패·경고·접수 여부 불명확 상태가 섞이면 완료로 표시하지 않는다.

현재가 REST 응답에는 가격 자체의 기준 시각이 없을 수 있다. **응답을 방금 받았다는 사실만으로 시세가 최신이라고 단정하지 않는다.** 구현 시 시장 상태·시세 시각 확인 수단을 검증하고, 유효성을 확인하지 못한 가격으로 주문을 보정하지 않는다.

## 6. 매수 가격 조정과 하락보완매수 합산

현재가를 `P`, 원래 주문가격을 `L`이라고 한다. 금액 비교는 부동소수점 오차 대신 정수 센트 또는 Decimal로 처리한다.

```text
매수 상한 U = P × 1.20를 유효 호가 단위로 내림
실제 매수가격 = min(L, U)

L > U  : U로 낮춤
L = U  : 그대로 유지
L < U  : 그대로 유지
```

**낮은 매수 가격을 현재가에 가깝게 올리지 않는다.** 최신 매수 조정은 +20% 상한이다. 보완매수 하한은 별도로 적용한다.

현재 하락보완매수는 `buildDownsideBuyOrders()`가 생성한다. 기본 매수수량이 `q`, 1회 매수금이 `B`일 때 각 단계는 다음과 같다.

```text
첫 보완매수: 가격 floor_cent(B / (q + 1)), 1주
다음 보완매수: 가격 floor_cent(B / (q + 2)), 1주
...
```

계획은 **원본 주문 목록을 기준으로 변환·합산**하는 방식이다.

- 기본 매수와 `U` 이상에 있던 보완매수는 실제 가격이 `U`로 같아지므로 수량을 합쳐 하나의 LOC 매수로 보낸다.
- 이때 포함한 보완매수는 별도 주문에서 제거한다. 기본수량을 늘린 뒤 같은 단계의 1주를 또 주문하지 않는다.
- `U` 미만의 보완매수는 기존 단계 가격을 유지하되, 아래의 -10% 필터를 적용한다.
- 전반전처럼 기본 매수가 둘이면 모든 원본 단계의 수량·완료 표식을 보존하면서 합산한다. 각 기본 주문에 무조건 `B / 새 가격`을 적용해 1회 매수금이 중복 배정되지 않게 한다.
- 기존 가이드의 보완 단계가 끝나는 지점보다 더 깊게 임의 확장하지 않는다.
- 합산 수량은 실제 1회 매수금과 기존 가이드로 계산한다. ‘60주면 무조건 70주’처럼 고정 가산하지 않는다.

## 7. 하락보완매수는 현재가 -10%까지만

```text
보완매수 유지 조건: 보완매수 원래 가격 >= P × 0.90
```

호가 단위로 하한을 표시할 때는 범위 밖 가격이 포함되지 않도록 올림한다.

- 현재가 $80 → 하한 $72.00.
- $72.00에 있는 보완매수는 포함한다.
- $71.99 이하는 제외한다.
- ‘72불쯤’의 주문을 새로 추가하는 뜻이 아니라, **기존 보완매수 단계 중 $72 이상인 것만 남기는 뜻**이다.
- -10% 필터는 **하락보완매수에 적용**한다. 원본의 일반 기본 매수·리버스 기본 매수까지 자동 삭제하는 규칙으로 확대하지 않는다.
- 개장 후 주가가 바뀌어도 장중 내내 범위를 다시 계산하며 주문을 늘리거나 정정하지 않는다. 당일 개장 주문 생성 시점의 기준가를 사용한다.

### 요청하신 $80 / $105 / 60주 예시

정확한 수량은 실제 1회 매수금에 따라 달라진다. 여기서는 **설명을 위해 `B=$6,300`을 가정**하고, 현재 앱의 보완매수 생성 함수로 계산했다.

| 항목 | 처리 결과 |
|---|---|
| 개장 후 현재가 | $80.00 |
| 원본 후반전 기본 매수 | $105.00 × 60주 |
| 매수 상한 | $96.00 |
| 상한으로 합쳐지는 보완매수 | 5개 단계, 합계 5주 |
| 최종 기본 매수 | **$96.00 LOC × 65주** |
| 따로 남는 하락보완매수 | $95.45 ~ $72.41에 총 22개, 각 1주 |
| $72 미만 보완매수 | 원본 60개 중 33개 제외 |
| 종가가 $72일 때 체결 대상 수량 | 기본 65주 + 보완 22주 = 87주 |

사용자의 ‘기본 매수에 보완 수량을 합산’하는 취지를 유지하되, 최신 +20% 상한과 이 예시 예산에서는 정확히 65주다. 실제 예산을 확인하지 않고 수량을 고정하지 않는다. 이 계산은 **주문 생성 예시**이며 체결 보장은 아니다.

보완매수는 더 낮은 종가에서 추가 수량이 체결돼 예산을 채우는 구조다. **모든 지정가×수량을 단순 합한 값과 실제 동일 종가 체결 금액은 다를 수 있다.** 증권사의 미체결 주문 증거금 예약은 별도로 확인해야 한다. 현금·주문 가능 금액이 부족하면 임의 환전이나 금액 증액 없이 경고하고, 사전에 정한 처리 방식을 적용한다.

## 8. 매도 주문 제외 규칙

```text
매도 지정가격 S >= P × 1.20 이면 해당 주문 제외
```

현재가 $80을 기준으로 하면 다음과 같다.

| 원본 매도 가격 | 결과 |
|---|---|
| $95.99 | 기존 가이드대로 제출 대상 |
| $96.00 | 정확히 +20%이므로 제외 |
| $105.00 또는 $105.10 | 제외 |

- 매도 가격을 $96으로 낮춰 제출하지 않는다. 제외 사유를 기록한다.
- 이 필터는 쿼터 LOC 매도와 최종 LIMIT 매도 각각에 적용한다.
- 가격이 없는 MOC는 이 비율 필터의 대상이 아니다. 기존 가이드의 리버스 첫날·현금 소진 등 MOC 분기를 유지한다.
- 매도 가격이 현재가보다 낮다는 이유만으로 이 +20% 규칙을 적용하지 않는다. 그 방향의 증권사 제한은 별도 검증 대상이다.
- 모든 매도가 제외돼도 사용자가 정한 정상적인 제외로 기록한다. 주문 오류와 구분한다.

## 9. 아침 차트 갱신과 실제 체결 반영

아침에는 **방금 끝난 미국 거래 세션**을 대상으로 처리한다. 한국 날짜를 주문일자로 그대로 사용하지 않고, 저장한 메리츠 주문일자와 주문번호로 연결한다. 날짜가 바뀐 뒤 ‘당일 주문’ 조회만 해서 전날 미국 주문을 놓치지 않는다.

1. 직전 세션의 캔들을 수집·저장한다. 아직 전략 모드는 변경하지 않는다.
2. 저장해 둔 자동주문을 날짜 범위 이력 조회로 대조하고, 주문별 상세 조회로 실제 체결 번호·시각·수량·금액을 확인한다. 미완료된 이전 세션도 함께 복구 대상으로 본다.
3. 원주문·정정·취소 행을 구분한다. 같은 주문의 누적 체결수량을 반복 조회할 때 전체 수량을 다시 더하지 않는다.
4. API 주문은 저장한 주문번호로 연결한다. 메리츠 앱 수동 주문도 연결 계좌·종목과 당시 가이드의 가격·수량·유형이 명확히 맞으면 연결한다. 다른 종목이나 연결이 불명확한 임의 주문을 이 전략에 넣지 않는다.
5. 실제 체결을 시간·주문 성격에 따라 묶고 기존 계산 함수를 재사용해 체결 입력을 만든다.
6. 체결 기록·현금·보유수량·평단·T·라운드를 DB에서 함께 반영한다. 같은 체결은 한 번만 반영한다.
7. 체결 반영 후 상태와 해당 세션 종가로 모드 전환·라운드 종료·예약 입출금 반영을 판단한다. 다음 거래일 가이드는 이 상태에서 계산한다.
8. 저장 완료 후 알림 기록과 푸시 발송 대상으로 등록한다. 푸시 실패 때문에 체결을 다시 입력하지 않는다.

현재 `syncMarketData()`는 캔들 저장 후 리버스→일반모드 전환까지 수행한다. 이 함수를 그대로 먼저 호출하면 **아직 체결을 반영하지 않은 평단·모드로 복귀 판단**할 수 있다. 구현에서는 캔들 저장과 전략 상태 전환을 분리하고, 수동 기록·기존 화면의 동작도 함께 검증한다.

### 반영 시 지켜야 할 데이터 의미

- 주문 접수만으로 현금·수량·평단·T를 체결된 것처럼 변경하지 않는다.
- 차트 종가가 주문 조건을 만족했다는 추정만으로 체결 입력하지 않는다. 메리츠 실제 체결을 원본으로 삼는다.
- 매수 지정가 $96이 실제로 $80에 체결되면 **$80의 실제 체결 금액·수량**을 반영한다.
- 수십 개 보완매수가 체결돼도 T를 주문 개수만큼 올리지 않는다. 해당 거래일의 기존 `buy_full` / `buy_half` 등 업무 의미에 맞게 한 번 반영한다.
- 같은 날 LIMIT 매도 후 LOC 매수, 쿼터매도와 최종매도, 리버스 매매의 순서를 기존 계산 의미와 맞춘다.
- 부분체결은 전량체결로 간주하지 않는다. 부분체결의 T 처리 기준은 구현 전 별도 확인하고, 확정 전에는 해당 건의 자동 전략 반영을 보류·경고하는 안이다.
- 수수료·현지 비용은 체결금액과 별도 저장한다. 현재 LTH 현금 계산에 포함하는 방식은 대조 후 확정하고, 계좌 전체 예수금으로 전략별 배정 현금을 덮어쓰지 않는다.
- 차트 수집 실패와 체결 조회 실패는 각각 기록한다. 확인된 체결 원본은 보존하고, 필요한 종가나 체결이 부족하면 전체 완료로 표시하지 않는다.

## 10. 완료·경고 알림과 아이폰 푸시

| 상황 | 알림 예시 | 판정 기준 |
|---|---|---|
| 개장 후 매수 접수 완료 | `SOXL 매수 주문 접수 완료 · 기본 65주, 보완 22건` | 제출 대상 매수가 모두 정상 접수됨. 체결 완료라는 뜻이 아님 |
| 아침 체결 반영 완료 | `SOXL 체결 반영 완료 · 매수 78주 · 보유수량·평단·T 갱신` | 실제 체결과 전략 상태의 DB 저장 완료 |
| 정상 미체결 | `SOXL 체결 확인 완료 · 매수 미체결` | 조회 완료, 실제 체결 0주. 매수 반영 성공으로 표현하지 않음 |
| 일부 주문 실패 | `SOXL 주문 일부 실패 · 2건 확인 필요` | 일부만 접수됐거나 경고·거절 발생 |
| 응답 유실 | `SOXL 주문 접수 여부 확인 필요` | 전송 시도 후 응답 불명확. 무조건 재주문하지 않음 |
| 아침 반영 보류 | `SOXL 체결 반영 보류 · 상태 불일치` | 부분체결 정책 미확정, 전략 버전 충돌, 계좌 대조 불일치 등 |
| 실행 누락·조회 오류 | `SOXL 자동주문 실행 확인 필요` | 개장 작업 누락 또는 시세·인증·체결 조회 실패 |

위 수량은 문구 예시다. 실제 처리 결과로 표시한다. 매수 대상이 0건이면 ‘매수 접수 완료’라고 알리지 않는다. +20% 매도 제외·-10% 아래 보완매수 제외는 일일 처리 요약에서 보여주며, 모든 정상 제외를 오류 푸시로 반복 발송하지 않는다.

아이폰 잠금화면 푸시는 Web Push로 구현하는 안이다.

- HTTPS, 웹앱 manifest, Service Worker, 푸시 구독 저장 및 서버 발송 기능을 추가한다.
- iOS 16.4 이상에서 홈 화면에 추가한 웹앱과 사용자의 알림 허용이 필요하다. 권한 요청은 사용자가 ‘알림 받기’를 누르는 동작으로 진행한다.
- 앱을 닫은 상태에서 실제 아이폰 잠금화면 도착을 검증한다. 집중 모드·OS 설정 등에 따른 표시 여부까지 서버가 보장한다고 표현하지 않는다.
- 알림은 앱 안에도 영구 보관해 푸시가 실패하거나 권한이 없어도 확인할 수 있게 한다.
- 알림마다 고유 이벤트를 저장해 재실행 시 앱 알림 중복 생성을 막는다. 발송 대기함을 사용해 푸시 실패만 재처리하고 체결 처리를 다시 실행하지 않는다.

근거: [WebKit의 iOS Web Push 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

## 11. 토글과 앱 화면의 변경 범위

- 기존 전략 화면에 자동매매 ON/OFF와 현재 처리 상태를 작게 추가한다. 기존 레이아웃·가이드·수동 체결 입력은 유지한다.
- 기본값은 OFF. 연결 계좌·종목·전략 상태가 확인된 전략만 활성화 가능한 구조로 설계한다.
- 전략별 원본 가이드와 실행용 주문을 분리 저장한다. 주문내역에서는 `원본 $105 × 60주 → 실제 $96 × 65주` 및 합산·제외 이유를 확인할 수 있게 한다.
- OFF는 **앞으로의 새 주문 중지**다. 이미 접수한 주문을 자동 취소하거나 체결 조회를 중단한다는 뜻으로 처리하지 않는다. 기존 주문은 아침까지 추적·반영한다.
- 이미 끝난 개장 시점 이후 ON으로 바꿨다고 즉시 주문하지 않는다. 다음 대상 세션부터 적용한다.
- 같은 계좌·같은 종목에 여러 전략을 동시에 활성화할 경우의 잔고 배분을 확정해야 한다. 초기안은 해당 조합에 자동매매 전략 하나만 허용하는 것이다.
- 메리츠 키는 서버에만 보관하며 클라이언트·알림·로그로 보내지 않는다. 공유 앱/다른 배포가 같은 계좌를 중복 집행하지 않도록 운영 대상을 구분한다.

## 12. 필요한 저장 구조와 실패 복구

아래 이름은 구현 시 정할 구조의 예시다. 이번 문서 작성에서 테이블을 생성하지 않는다.

| 구조 | 보관할 내용 |
|---|---|
| 자동매매 설정 | 전략, 연결 계좌 식별자, ON/OFF, 적용 시작 세션 |
| 일일 실행 기록 | 미국 세션 날짜, 전략 버전, 원본 가이드, 현재가·수신시각, 조정 규칙, 처리 상태 |
| 주문 기록 | 원본 주문 묶음, 실제 가격·수량·유형, 제출 시도, 메리츠 주문일자·번호, 접수·경고·거절·불명확 상태 |
| 체결 원본·반영 기록 | 체결 번호·시각·수량·금액, 누적량/개별량 구분, LTH 실행 기록 연결, 반영 여부 |
| 알림·발송 대기함 | 이벤트 고유키, 알림 본문, 읽음 상태, 푸시 처리 결과 |
| 기기 구독 | 승인된 기기의 Web Push 구독 정보 |

중복 방지는 세 층으로 나눈다.

1. 같은 세션 작업이 두 번 동시에 시작되지 않도록 잠금과 일일 고유키를 둔다.
2. 같은 주문은 제출 전 의도를 저장한다. 접수 응답을 잃으면 `unknown`으로 남기고 주문내역과 대조한다. 조회 결과가 불명확하면 자동 재전송하지 않는다.
3. 체결·전략 상태 반영은 고유 식별자와 버전 검사를 포함한 DB 트랜잭션으로 한 번만 처리한다. 현금 조정·수동 입력과 충돌하면 덮어쓰지 않는다.

LTH의 기존 `request_id`·전략 버전·`commit_strategy_execution`은 3번의 기반으로 재사용한다. 이것만으로 **메리츠 외부 주문까지 중복 방지되는 것은 아니다.** 외부 주문과 DB 저장은 단일 트랜잭션이 아니므로 2번의 응답 유실 복구가 별도로 필요하다.

또한 현재 스케줄 문서상 Cron은 중복 호출·누락 가능성이 있다. 정상 실행 로그뿐 아니라 개장 작업 누락을 감지하는 점검도 필요하며, 이때는 뒤늦은 주문 대신 경고한다. 푸시 장애를 포함한 외부 서비스 실패를 ‘반드시 도착’으로 보장하지 않는다.

근거: [Vercel Cron의 중복·누락 및 동시 실행 안내](https://vercel.com/docs/cron-jobs/manage-cron-jobs).

| 6 | 토글·앱 내 알림·아이폰 푸시 | 390px·320px 화면, 권한 거절, 앱 종료·잠금화면 알림 |

| 8 | 사용자 운영 환경에서 별도로 가동 확인 | 주문 접수·체결·반영·푸시를 각각 검증. 모의 테스트만으로 실주문 성공을 주장하지 않음 |

핵심 경계 예시는 다음과 같다.

- `P=80`: 매수 $96는 유지, $96.01은 $96로 조정.
- `P=81`: 매수 $97.20은 유지, $97.21은 $97.20으로 조정.
- `P=80`: 매도 $95.99는 제출 대상, $96는 제외.
- `P=80`: 보완매수 $72는 포함, $71.99는 제외.
- 예산 $6,300·기본 60주·기준가 $80: $96×65주 + 기존 $95.45~$72.41 단계 22건, 중복 없음.
- 전반전 기본 매수 두 줄이 합쳐져도 예산·반회/1회 매수 의미를 중복 적용하지 않음.
- 리버스 첫날·현금 소진 MOC 유지. 가격 없는 매도에 가격 필터를 잘못 적용하지 않음.
- 주문 10개 중 일부만 접수됐을 때 전체 성공 알림을 보내지 않음.
- 접수 응답 유실 후 같은 세션 작업이 재실행돼도 중복 주문하지 않음.
- 아침 작업을 반복 실행해도 체결·T·현금·라운드가 중복 변경되지 않음.
- 체결 조회 전에는 리버스 복귀로 전략 상태를 먼저 변경하지 않음.
- 매수 접수 완료, 실제 미체결, 실제 체결 반영 완료를 각각 구분해 알림.

## 14. 구현 전에 남은 결정·확인

이미 확정한 **+20% 초과부터 조정**, **잠금화면 푸시**는 다시 묻지 않는다. 아래는 아직 확정되지 않은 항목이다.

1. **적용 전략·종목:** SOXL 전략 우선인지, TQQQ에도 같은 규칙을 적용할지. 토글은 전략별로 두는 안이다.
2. **부분체결의 T:** 계획 수량의 일부만 체결됐을 때 기존 반회/1회 기준을 어떻게 적용할지. 확정 전 자동 T 변경은 보류하는 안이다.
3. **운영 환경·계좌 배분:** 개장 시분을 지원하는 스케줄러, 동일 계좌·동일 종목의 전략 중복 활성화, 주문 가능 금액 부족 시 제외 순서.
4. **메리츠 실제 제한:** SOXL 정규장 LOC의 기준 가격·허용 범위·경고 확인 여부. 사용자 관찰은 $81 기준 약 +29.63% 접수 / 약 +35.80% 거절이며, 정확한 30% 경계는 미확인이다.
5. **현금 대조 세부사항:** 수수료·현지 비용 반영 방식과 계좌 전체 현금/전략별 배정 현금의 관계.
